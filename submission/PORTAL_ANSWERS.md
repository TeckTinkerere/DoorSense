# Portal answers (each field is limited to 150 words)

## What does your solution do?
DoorLens is a web app that turns train sensor data into an answer a maintainer can act on. For Door, drop in the continuous motor recording: it finds every open/close cycle (exact start and end times) and labels each Normal or Abnormal resistance, showing the motor current against a normal reference so the label is explainable. A "Challenge this result" tool re-runs the model on a synthetic recording change (for example current -5%) to show whether a label is fragile. For ACV, upload the eight-car workbook: it ranks the cars from most to least likely to have the refrigerant leak, with a temperature-gap chart and per-car table. Both export CSVs in the exact challenge format, and a plain-language "How this works" page guides first-time users. It is an offline analysis aid, not a safety system.

## What tech stack was used to build this solution?
Backend: Python 3.12 with FastAPI and Uvicorn, NumPy and pandas (calamine for fast Excel reading). Door uses direction-specific logistic regression on 21 cycle features with frozen, checksummed JSON coefficients and pure NumPy inference. ACV uses a parameter-free peer-comparison score. Frontend: Next.js (static export), React and Plotly. Testing: pytest (43 passing), Playwright browser checks, and a live-server synthetic scenario harness. Packaging and hosting: Docker, Cloud Build and Google Cloud Run in the hackathon project, with the code on GitHub.

## What challenges did you face, and how did you overcome them?
Very little labelled data: 110 door cycles and six ACV cases. We avoided overfitting by keeping the Door model small and using ordered, leakage-free folds, and by making ACV a parameter-free peer comparison rather than a fitted model. Because the data lacks door and session identities, we state that results may be optimistic. We stress-tested with 59 synthetic scenarios against the live app; this exposed Door's sensitivity to voltage drift (F1 0.82 at +10%), which we report openly. During deployment, model checksums failed on Linux because of line-ending changes; we fixed this by storing model files byte-for-byte and verified the hosted app reproduces our submitted predictions exactly.
